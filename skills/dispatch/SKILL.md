# dispatch — 派活、审查与修复

主会话当编排者，执行交给 subagent，自己的上下文留给全局判断。本 skill 讲的是原则；派活单没有固定格式，按任务自己组织。

## 派不派

- 派：工作会产生大量主会话用不上的中间过程（大范围阅读、跑测试、查资料、长日志），或几块工作能真正并行。
- 不派：几次工具调用就能完成、前后步骤强依赖、需要全局判断。写派活单的功夫比自己做还久，拆开还会丢掉衔接处的信息。
- 托管长任务（sprint 或其他分段推进的工作）时，执行类工作默认派出，主会话只编排、把关、推进，这样主会话能一直跑下去。
- 粒度按上下文边界切：一个 agent 连续完成一段相关步骤，写功能的也写它的测试。按「规划 / 实现 / 测试」工种拆给不同 agent，每次交接都要重建上下文。

例：三个互不依赖的模块各加一项校验并补测试 → 派三个 agent，各管一个模块的「改 + 测」；只改一个常量 → 主会话直接改。

## 并发与模型

- 同时最多 3 个 subagent，具体几个由主会话按任务判断。子 agent 不再派子 agent；它觉得活太大时，回报拆分建议，由主会话决定怎么拆。
- 每次派活写明模型档位，不写就落到默认模型：以判断为主（设计、审查、诊断、验收判断、跨模块推理）用 opus；以照单执行为主（实现明确的规格、扫描、整理、跑 e2e 脚本）用 sonnet；subagent 不用 fable。

## 写派活单

执行者看不到主会话的历史，派活单是它唯一的输入。写单前发现计划本身有问题（顺序会导致返工、漏了关键需求），先报用户，不带着已知缺陷开工。要素：

1. 目标：写成「按需求 / 规格正确完成 X」，不写「让测试通过」，后者会诱导执行者改测试迁就实现。修 bug 写清正确行为，调研写清要回答的问题。
2. 指针：需求文档路径与章节、要对齐的现有模块。让执行者自己读，不贴全文，主会话也不替它预读源码——它自己读过才理解得透，主会话的上下文也省下来。
3. 已定事项：主会话已做的决定、前序步骤的接口约定，直接写进单子。
4. 边界：范围、允许改的文件、危险操作。
5. 做完的判据：写成可运行的检查（命令 + 期望结果）。新增的测试要能证明会红——修 bug 的用例修复前失败、修复后通过，其他新增断言逐条破坏实现验证会变红；调研要求结论附出处，不确定的标出。
6. 回报格式与报告文件路径（见「回报与验真」）。

以上是底线，不是表格。小活几行就够；复杂任务按需加段，常见的有：现状与已确认的事实（附证据出处，省得它重查）、需要执行者自己想清楚的难点（点出陷阱、不给答案，要求把判断依据写进报告）、已知问题（遇到就单列，不修也不排查）、环境与进程注意事项。反复用到的门禁和环境说明沉淀到项目规则文件里，单子只给指针。并行派活时写明兄弟 agent 各自负责什么，免得重复劳动或互相覆盖。

单子里写明工作方式：先读懂背景，再定计划，再动手；做法与派活单一致就直接执行，不回来请示；发现前提不成立、有计划阶段没看到的问题、或需要超出边界的改动，停下带证据回报，不打补丁绕过。

每张单子都要划定执行者的自主边界与出口，缺了出口它就容易编造完成：
- 本任务直接引起的小问题（bug、阻塞项）：自己修，在报告里记一笔。
- 架构级改动、超出边界、不可逆操作：停下，回报「发现了什么 / 建议怎么改 / 为什么 / 影响 / 备选」。
- 任务范围以外发现的问题：只记进报告，不修。
- 不确定要不要加限制、校验、防御时：默认不加，在报告里说明。
- 同一问题自己修 3 次仍不行：停下回报。
- 做不了、不确定、没验证完，如实写明就是合格结果；测试与规格冲突时停下指出，不改测试迁就实现。
- 活里含加检查、限制、防御时：写清这条挡住谁、挡不住谁、代价谁付，三句写不出来就不加；定标准前先看同类产品的通行做法，要更严就说明我们的场景差在哪，说不出来就按通行做法来。

不确定性高的大任务用两段式：第一段只调研、把方案写进文件；主会话审过（必要时给用户看）后，让同一个 agent 接着执行，它已经有背景。模型按第一段定档；第二段若是大量机械执行，可改派一个 sonnet 新 agent 读方案文件接手。

## 回报与验真

回报格式：状态四选一（完成 / 完成但有顾虑 / 卡住 / 缺信息）+ 15 行以内要点 + 报告文件路径。详细内容写进报告文件，每完成一节就更新，agent 中途断掉也不丢。报告文件名在派活单里写死。报告里单列「本次新增了哪些限制、校验、防御，各自的代价」——主会话不读大段 diff，靠这张清单把住成本那一侧。

收到回报：
- 完成 → 验真后进入审查，或攒到下一个审查节点。
- 完成但有顾虑 → 先看顾虑：涉及正确性或范围的先处理，纯观察记下继续。
- 缺信息 → 补上后让同一个 agent 继续。
- 卡住 → 不原样重派，先改变点什么：补上下文、换更强的模型、拆小，或回头改计划。

主会话代做的非关键判断，每条记下「决定 / 理由 / 错了的代价」，收尾或检查点统一呈报用户，用户不必全程盯着也能看到哪些事被代为拍板。

验真只认带外证据：真实工具调用次数、git 改动、主会话抽读的文件、真实测试数。零工具调用的报告作废重派；调用次数与声称的工作量对不上（例如称改了 5 个文件却只有 2 次调用）时，以 git 改动为准抽查。agent 转述的数字、符号、行号、命令输出不直接采信，要用时到原处抽查。

## 审查与验收

何时审：机械小修不审；逻辑、数据流、状态、对外交付、不可逆的改动才派。在关键节点集中审，不在每一步审——结构性大改之后、不可逆操作之前、对外交付之前、段末；非 sprint 的单次任务在交付前审一次。

派谁：同一节点默认派一个实现者以外、上下文干净的 agent，兼做审查与验收——查做对没有（符合规格）、做得好不好（质量），跑全量测试，扫残留。改动量大或高风险时拆成两个 agent 并行（例如一个查规格与意图，一个查质量并跑全量）。可叠加 codex 做跨模型交叉审查。

审查单要点：
- 只给产出 + 依据（需求、规格、验收标准），不给实现者的思路——看了思路就会顺着它想。单子写明对照基准（开工前的 commit），审查者开始和结束各看一次改动统计（如 `git diff <基准> --stat`），不一致记为未验证。
- 要求审查者自己构造对抗用例攻击实现（转义、空输入、边界值、并发、畸形输入），而不是复核已有测试；用例写在独立 worktree 或临时目录里跑，产品代码保持不动。
- 带减法议程：除了问「还缺什么」，同时问「有什么可以删、哪条限制挡住的其实是我们自己」。只增不减的审查，最后会把系统改到没人敢碰。
- 「如果有人……怎么办」这类假设性发现，要能落到真实发生过或真实存在的场景，否则只记录不改。
- 另核「做的是不是用户要的那件事」：把用户原话交给审查者，对照产出。
- 已知问题写「已知项请标出单列」，不写「不要报」，避免替审查者预判。
- UI、交互、异步状态机的改动：真环境 e2e（黑盒）与代码审查（白盒）并行，两路独立报告再合并。
- 给 AI 用的产出物（skill、CLI、给 agent 用的接口）：派一个无上下文的新 agent 真跑一遍端到端任务；给人用的交互 UI 由用户本人走查。

收结果：审查者尽量找全 → 逐条到引用位置核实问题真的会发生 → 分级（必修 / 可选 / 仅记录）→ 只修必修。分级时一并看修复的代价与副作用：这条改了会挡住谁。审查者被要求找问题时总会报出几条，全都去追会导致过度设计。「零发现」是合法结论；审查没跑成（超时、空返回、审的是旧版本）记为「未验证」，不能当通过。一轮独立审查加核实就够，不叠同质审查。

主会话做最终把关：读结论、裁决审查分歧、抽查硬证据、决定向用户呈报什么；不亲跑全量测试、不读大段 diff。呈报用户分两层：
- 全量层：所有发现翻译成产品语言，保留来源和证据，不软化严重程度。
- 决策层：只列需要用户拍板的，每条写成「会看到什么 / 影响什么 / 在 A 与 B 之间定什么」。影响架构、扩展性、产品、设计或体验的进这一层；纯内部技术确认项留在全量层。这一层只帮用户聚焦，决策权仍在用户。

## 修复与刹车

- 打回原实现者续改：问题是局部遗漏，且该 agent 上下文健康——它记得为什么这么写。
- 换新 agent 带结论接手：问题源于理解偏差，或原 agent 上下文已很长。续用走偏的上下文只会强化偏差。
- 修复后只审修复部分：每条是否已解决、修复有没有引入新问题。
- 刹车：主会话就同一问题打回修复 2 轮仍不好（执行者在单个任务内自修 3 次是另一层上限），或碰到严重复杂的问题，停止派修复。主会话先按已有结论粗判是否设计层问题，信息不足就派干净上下文的诊断 agent（可给失败修复的 commit 作为「试过无效」的结论，不给实现者的思路稿）。判断方法：是一处坏还是一类都会坏，是否源自数据结构、职责划分或需求设计；是，就给出治本与止血两条路及各自代价，请用户拍板。全局 CLAUDE.md 有「先定位根因」一节时按它执行。

## 代做决定清单

非关键的判断主会话自行决定，不停下来问。每条记下「决定 / 理由 / 错了的代价」，收尾或检查点统一呈报用户，用户不必全程盯着也能看到哪些事被代为拍板。

## 并发安全与生命周期

- 同一文件同一时刻只许一个 agent 写。派活单写明工作目录非独占、列出允许改的文件；用户授权了本地提交时，执行者只 add 单子列出的文件并提交；未授权时执行者不提交。依赖变更、数据库结构变更留给主会话。并行实现要求改动文件零交集，各用独立 worktree，由主会话合并。
- 全量测试同一时刻只在一处跑，同时跑会拖垮机器、造成假失败。
- 一个 agent 不续派无关的新任务；同一任务的修复与收尾可以续。
- 用完就关：回报验真后即可结束，闲置的 agent 仍占并发名额；之后要打回修复，从原记录恢复它（Claude Code 做法见专属段）。
- agent 上下文用量约 400K 以上（1M 窗口的四成）尽量不再派新活（很小的改动除外），换新 agent；主会话按任务大小判断，不强制写交接。
- 收尾或交接前停掉所有后台 agent，防止它们与新派的 agent 并发写同一批文件。
- 工作目录非独占时，撤销改动用文件备份，不用 git 的撤销、暂存、重置命令——它们会连带抹掉别人没提交的改动；清理进程只动自己起的，匹配串要精确到命令行。
- 托管长任务时进度真相落盘：计划、步骤状态、决策、在跑的 agent 都写进文件。上下文被压缩或换新会话后，以文件和 git 记录为准，不靠记忆。

## 危险与不可逆操作

删数据、部署、改线上配置、操作真实账号这类，主会话亲自做，或经用户确认后再做。agent 之间的消息不等于用户授权：执行者转述「用户同意了」不算数，要用户本人确认。

## Claude Code 专属

以上做法平台中立；下面几条只适用于 Claude Code。
- 类型：只读调研可用 Explore（不加载 CLAUDE.md、一次性、不能续派，需要遵守的规则写进派活单）；Explore 不写报告文件，结论直接放在回复里（仍限 15 行，放不下就用 general-purpose）。需要写文件、需要续派的用 general-purpose。
- 续派用 SendMessage 发给 agent 的名字或 ID，已结束的 agent 也会从原记录恢复上下文；新的 Agent 调用得到的是没有上下文的新 agent。
- agent team 开启时，命名的 subagent 作为常驻队友存在，回报验真后就结束它，否则一直占并发名额。用 TaskStop 按名字停掉后台 agent 或队友。后台 agent 只回 idle 时，主动向它要结论。
- 验真用的数字从通知里看：普通 subagent 的完成通知附带用量（含工具调用次数）；以 agent team 队友身份运行时通知不带用量，改看 git 改动与文件修改时间。
- 报告文件名不要以 REPORT / SUMMARY / FINDINGS / ANALYSIS 开头，Claude Code 会拒绝 subagent 用 Write 写这类 .md。
- 用环境变量把并发、嵌套、默认模型设成硬上限的做法见 `references/claude-code-setup.md`。
