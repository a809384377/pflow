# 接管已有项目：补建结构真相体系

适用于代码已经成形、迭代过多轮，但没有 `ai/tech-design/` 的项目。这条路径**不当场把机制文档写完**：初始化只做三件轻活——盘点现状、立骨架、定缺口清单，反向测绘的重活交给自动创建的「真相补建 sprint」，用既有 sprint 机制分步推进、可派 subagent 并行。

入口：

- 用户显式要求整理历史项目的架构/结构文档；
- 任一初始化路径检测到项目有 `ai/PROJECT.md` 等过程文件、但 `grep -m1 '^结构真相体系:' ai/PROJECT.md` 无命中时，一次性询问「启用并补建 / 现在只标注不启用」。用户选不启用就写「未启用」标注收场，本次不再追问。

标注行格式、骨架内容、校验件挂载见 `truth-doc-setup.md`；文件模板见 `truth-doc-templates.md`；写作纪律与编号见 `truth-doc-guidelines.md`。

## 步骤 1: 盘点现状（只读）

```bash
git ls-files | sed 's|/.*||' | sort | uniq -c | sort -rn   # 顶层目录与文件规模
git log --since='3 months ago' --name-only --format= | sed '/^$/d' | sort | uniq -c | sort -rn | head -30   # 近期活跃文件
ls ai/ ai/sprints/archive/ 2>/dev/null                      # 已有过程文件与历史 sprint
```

同时读已有的结构类文档（README、旧 TECH-DESIGN、`docs/`、`ai/specs/` 定稿 spec），判断哪些内容可直接转成机制文档初稿。

向用户汇报：项目规模与主要模块、近三个月活跃模块与静默模块的划分、已有结构文档中可复用的部分。活跃/静默的划分决定后续测绘的深浅，是清单确认的重要依据。

## 步骤 2: 立骨架 + 写标注

按 `truth-doc-setup.md` §2-§4：写入「已启用」标注行、复制 `check.sh` 并挂进测试命令、建 `README.md` 门户与 `code-map.md`。此时门户的文件清单与路由表可以只列出计划中的机制文档；`code-map.md` 先写模块地图与已确认的模块条目，机制条目随测绘补全。

## 步骤 3: 缺口清单，经用户确认

依据盘点结果和 `truth-doc-guidelines.md` §2 的类型侧重清单，列出「该有哪些机制文档、现缺哪些」，用表格呈报：

| 文件 | 职责 | 覆盖源码范围 | 测绘深度 | 依据 |
|---|---|---|---|---|
| `00-boundary.md` | 系统边界、外部依赖、不负责的事项 | 全仓库 | 深 | 第一次接手必读 |
| `10-<机制名>.md` | `<机制当前如何运作>` | `src/<目录>/` | 深 | 近三个月高频改动 |
| `30-<机制名>.md` | `<机制当前如何运作>` | `src/<目录>/` | 粗 | 半年未动，先写边界与入口 |

最容易漏掉的两类，逐项对照有没有覆盖：

- **运行时视图**：一次典型请求 / 命令 / 任务从入口到落盘经过哪些模块，失败时怎么走；
- **横切机制**：配置与环境变量合并、鉴权与权限、错误与重试、并发与锁、日志与可观测、构建与发布。

用户增删确认后的清单，就是补建 sprint 的 BRIEF 内容。清单未确认不创建机制文档。

## 步骤 4: 创建「真相补建 sprint」

项目已有活跃 sprint 时不抢占：把确认后的缺口清单写入 `ai/ROADMAP.md`（标注来源），待当前 sprint 结束再开补建 sprint。

无活跃 sprint 时，按 `/pflow-sprint` 的 create 流程创建 `ai/sprints/active/truth-backfill/`，文件模板见 pflow-sprint 的 `references/templates.md`：

**BRIEF.md**
- 问题描述：项目已有代码但无结构真相文件，新会话接手要重读源码；
- 成功标准：确认清单内每份文档建成并通过 `truth-doc-guidelines.md` §6 自检；`code-map.md` 覆盖全部已确认机制；`bash ai/tech-design/check.sh` 红灯为零；黑盒验收通过（见下）；
- 范围：只写真相文件，不含代码改动；清单外的机制不在本期。

**PLAN.md**
- 按机制分步，一步产出一份或一组强相关的机制文档，每步可独立验证；
- 深浅分级：活跃模块深读源码后写全协作关系与时序；静默模块先写边界、入口与源码落点，正文标注为粗测绘，等到该模块被改动的那轮 sprint 收尾再补深；
- 每步的验证方式：该文档 frontmatter `sources` 路径存活、图节点名与 `code-map.md` 条目名一致、跑一次 `check.sh` 该文档无红灯；
- 末步统一收口：补齐 `code-map.md` 反查表、门户文件清单与路由表，跑全量校验件。

**派活边界**（大仓库防止单 agent 上下文爆掉；派活单写法、并发与审查做法见 dispatch skill）
- 一个 subagent 负责一份机制文档或一组强相关文档，只给它该机制的源码入口、`truth-doc-templates.md` 与 `truth-doc-guidelines.md`，产出直接写盘；
- 不让任何 agent 通读全仓库；跨机制的公共信息（模块地图、命名）由主会话在末步统一收口；
- 并行派活时按模块划分文件归属，避免两个 agent 同时改 `code-map.md`。

**黑盒验收**（本 sprint 的成功标准之一）
派一个无项目上下文的新 agent，只给它 `ai/tech-design/README.md` 一个入口，令其完成一个典型任务，例如「说明 `<某机制>` 的数据流，并指出要改 `<某行为>` 需要动哪些文件」。它卡壳的地方就是文档缺陷——补完再复测一次。
