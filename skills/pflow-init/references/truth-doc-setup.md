# 结构真相体系：启用询问与骨架搭建

本附件供 `pflow-init` 的任一路径使用：与用户确认启不启用结构真相体系，把选择写成 `ai/PROJECT.md` 的固定标注行；启用时搭出 `ai/tech-design/` 骨架并把校验件挂进项目的测试命令。

配套附件：生成顺序、类型侧重、编号、写作纪律、图规范见 `truth-doc-guidelines.md`；四类文件骨架见 `truth-doc-templates.md`；校验件本体是同目录的 `check.sh`。接管代码已成形的历史项目见 `truth-doc-adopt.md`。

## 1. 询问是否启用

一次问清，附判据让用户能直接判断：

> 这个项目要启用「结构真相体系」吗？启用后会建 `ai/tech-design/`（门户 + 一机制一文件 + 代码地图 + 校验脚本），此后每轮 sprint 收尾会强制复核并回写受影响的机制文档。
> 建议启用：会持续开发、多个模块相互协作的代码项目——新会话或新 agent 接手时靠它快速建立结构认知，不必重读源码。
> 不必启用：单文件脚本、命令片段集、素材或纯文档项目——维护真相文件的成本大于收益。

用户选择不启用，同样要写标注行：没有标注的项目，sprint 收尾每次都会提示一次。

## 2. PROJECT.md 标注行

标注行是后续所有流程的分岔依据。写在 `ai/PROJECT.md`「## 项目结构」段的末尾，独占一行、行首无缩进、无引号无列表符号。二选一：

```
结构真相体系: 已启用 -- 结构真相文件在 ai/tech-design/，改代码前先读 ai/tech-design/README.md
```

```
结构真相体系: 未启用
```

「已启用」行的破折号之后可按项目实际补充说明，检测只看行首前缀与状态词。检测方式（任何流程通用）：

```bash
grep -m1 '^结构真相体系:' ai/PROJECT.md
```

| 检测结果 | 状态 | 后续流程的行为 |
|---|---|---|
| 命中且含「已启用」 | 启用 | sprint 收尾强制执行结构真相回写 |
| 命中且含「未启用」 | 明确不启用 | sprint 收尾整步跳过，不出现提示 |
| 无命中 | 无标注 | sprint 收尾一次性提示可补建或标注不启用，不阻塞收尾 |

标注可随时改变：未启用的项目日后想启用，走 `truth-doc-adopt.md` 的接管流程；已启用的项目要退出，把标注改成「未启用」并告知用户 `ai/tech-design/` 会停止维护。

## 3. 搭骨架（仅启用时）

目标结构：

```
ai/tech-design/
  README.md        门户：文件清单 + 阅读顺序 + 问题式路由表 + 一张系统级图
  code-map.md      模块地图 + 「机制/概念 → 源文件」反查表
  NN-<机制名>.md    一机制一文件，清单经用户确认后创建
  check.sh         校验通用件副本，挂进项目测试命令
```

执行顺序：

1. **复制校验件**：把本 skill `references/check.sh` 复制为项目的 `ai/tech-design/check.sh`，并 `chmod +x`。脚本零依赖（bash + git），自行定位 Git 根目录——项目尚未 `git init` 时，先完成初始化再跑校验。
2. **拟机制文档清单**：按 `truth-doc-guidelines.md` §1 的生成顺序与 §2 的类型侧重清单，结合项目实际模块拟出占位清单，每条写明文件名、职责一句话、覆盖的源码范围。
3. **清单经用户确认**：机制清单定义了真相体系的边界，属产品决策——展示清单，用户增删确认后再创建文件。不为凑齐类型条目建空文档。
4. **生成文件**：按 `truth-doc-templates.md` 生成门户、已确认的机制文档、`code-map.md`，剥掉模板的外层 `~~~` 围栏，用项目事实替换全部占位符。
5. **挂进测试命令**：见下方 §4。
6. **CLAUDE.md 项目入口**：加入指向门户的那一行，措辞见 SKILL.md「生成模板」中的 CLAUDE.md 模板（已有项目适配路径在「处理 CLAUDE.md」那步一并加）。

**代码尚未成形的新项目**：机制还没落地，此时只建门户与 `code-map.md` 骨架（可只写系统边界与预期模块），机制文档留待首个 sprint 收尾按实际落地的机制补建。给用户说明这一点，避免把设想当成现状写进真相文件。

## 4. 把校验件挂进测试命令

挂上以后，文档腐化会在跑测试时变成红灯，而不是等人发现。

| 项目形态 | 挂法 |
|---|---|
| npm / pnpm 项目 | `package.json` 增 `"lint:docs": "bash ai/tech-design/check.sh"`，并让 `test` 先跑它，如 `"test": "npm run lint:docs && vitest run"` |
| Makefile 项目 | `test` 目标首行加 `bash ai/tech-design/check.sh` |
| Python 项目 | 在 `make test` / `tox` / `nox` 的测试入口首行串一行；无统一入口时挂 pre-commit hook |
| 其他有 CI 的项目 | 挂在 CI 测试 job 的第一步 |
| 无任何测试命令 | 在 `CLAUDE.md`「关键命令」段写入 `bash ai/tech-design/check.sh -- 结构真相校验`，由 sprint 收尾流程执行 |

挂完当场跑一次，确认输出以 `OK` 或 `WARN` 结尾。输出 `ERROR` 表示脚本前置条件不满足（不在 Git 仓库内、缺 `ai/tech-design/` 目录），先修前置条件。

校验分级：L1 文档中的源码路径失活、L3 指向 `ai/` 内部的文件指针失活为红灯（挡测试）；L2 源文件未登记 code-map、L4 图节点名与 code-map 条目名不一致、L5 `last_reviewed` 超期、L6 单份文档超行数阈值为黄灯（报告不挡）。黄灯误报多时，在 `ai/tech-design/check.conf` 覆写阈值与豁免清单，可配置项见 `check.sh` 头部注释。

## 5. 交付前自检

文档内容自检见 `truth-doc-guidelines.md` §6，此外确认：

- [ ] `ai/PROJECT.md` 有标注行，格式与 §2 一致，`grep -m1 '^结构真相体系:'` 能命中。
- [ ] 启用时 `ai/tech-design/check.sh` 存在、可执行，已挂进测试命令或已写入 CLAUDE.md 关键命令。
- [ ] 启用时当场跑过一次校验件，红灯为零（黄灯可留，逐条向用户说明）。
- [ ] 启用时 `CLAUDE.md` 项目入口含 `ai/tech-design/README.md` 指引。
- [ ] 机制文档清单经用户确认，没有未经确认就创建的文档。
