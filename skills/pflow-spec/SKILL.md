# /pflow-spec — 设计方案阶段

把一个需求从「想做」推进到「想清楚」，产出一份冻结的设计 spec，作为后续 sprint 执行的唯一依据。

核心价值：**在执行前暴露方案分歧**。在文档上改方案的代价，远小于在半截代码里发现方向错了。这个阶段就是用一轮对话把关键决策钉死，让后面的执行只剩「怎么做对」，不再纠结「该不该这么做」。

## 何时用 / 何时跳过

值得走 spec 的信号：需要在多个方案间权衡、涉及数据结构或架构、跨多个模块、有不可逆的取舍、你（用户）想先对齐再动手。

直接跳过（进 /pflow-sprint 或直接改）：单文件改动、配置调整、文案更新、原因和方案都清楚的 bug 修复。

spec 阶段是**可选前置**，不是 sprint 的强制入口——简单工作不该被这套流程拖慢。

## 产出

`ai/specs/YYYY-MM-DD-<topic>-design.md`（目录不存在则创建）。这份 spec 一旦定稿就冻结，commit 留痕；后续 sprint 以它为准，需求或方向根本变化才另起新 spec。

冻结的 spec 是决策蓝图，只追加不改写——被后续 spec 部分推翻时不重写正文，只在被推翻的章节打修订标注、更新状态字段（三态与标注格式见 `references/spec-template.md`）。

## 流程

```
1. 取题
   读 ai/PROJECT.md + ai/ROADMAP.md + ai/KNOWLEDGE.md。
   有 ai/tech-design/README.md 门户就按它的问题式路由表读相关机制文档，弄清要动的机制现在怎么运作。
   把 KNOWLEDGE 里与本需求相关的规则/模式拉出来，作为设计约束带进对话。

2. 对话设计（见下方「对话原则」）
   一次一问澄清目标与边界 → 给 2-3 个方案带取舍与推荐 → 分节呈设计、逐节增量确认。

3. 冻结 spec
   写 ai/specs/YYYY-MM-DD-<topic>-design.md（结构见 references/spec-template.md）。
   本 spec 推翻了旧 spec 的部分结论时，回旧 spec 给被推翻的章节打修订标注、更新其状态字段
   （操作与格式见 references/spec-template.md §冻结后的修订标注）——标注由推翻它的新 spec 负责打。
   commit，标注「设计定稿冻结于 commit <sha>」。

4. spec 自检
   占位符 / 内部矛盾 / 范围是否聚焦到可单次实现 / 有无两义表述 / 被推翻的旧 spec 章节是否已标注，就地修。
   清单见 references/spec-template.md。

5. 用户复核
   请用户过目 spec，确认或修订后再往下。

6. 交棒（解耦）
   询问是否直接转 /pflow-sprint create 落地为执行计划。
   也可以停在「只出 spec」——spec 是独立产物，不绑定必须开 sprint。
```

## 对话原则（借鉴 brainstorming，按需用）

这些是让设计对话高效的习惯，不是僵硬步骤——根据需求复杂度灵活取舍：

- **先探上下文再发问**：先看项目现状（PROJECT/ROADMAP/KNOWLEDGE/现有代码），带着 context 提问，减少用户负担。
- **一次一问**：澄清式问题一次问一个，别一口气抛一堆。多选题比开放题更省用户力气。
- **给方案而非只给问题**：关键分岔处给 2-3 个方案，各自点明对体验/成本/风险的影响，并给出你的推荐和理由——让用户做判断题，不是问答题。
- **审查/分析发现分两层呈报**：对 spec 派了独立审查或跑了技术分析后，先全量忠实列出（都报、不软化、保留来源），再附一段决策摘要，只列要用户拍板的——让用户大概率只看摘要就能拍板。派审查与两层呈报的写法见 dispatch skill「审查与验收」。
- **增量确认**：设计分节呈现，每节确认再往下，发现不对随时回退。
- **YAGNI**：砍掉不必要的功能；范围越聚焦，spec 越实现得动。

## 范围过大时

如果需求其实是多个独立子系统（如「做一个含聊天、存储、计费、分析的平台」），先帮用户拆分：哪些是独立块、彼此关系、先做哪个。每个子块各自走一轮 spec → sprint，不要把巨型需求塞进一份 spec。

## 与 sprint 的关系

spec 写「做什么 / 为什么 / 技术方案」；sprint 的 PLAN 写「执行步骤怎么拆」。spec 是 sprint 的输入，但二者解耦：spec 可独立存在，sprint 也可不依赖 spec 直接开。
