# 设计 spec 模板

设计 spec 是 sprint 执行的唯一依据，面向「第一次接手、没有本次对话记忆」的读者写：他读完应能独立理解做什么、为什么这么定、边界在哪。各段按需裁剪，简单方案删掉用不上的段，别为凑结构写空话。

---

## 文档结构

```markdown
# 设计方案: <标题>

## 状态
草稿 / 定稿（冻结于 commit <sha>）/ 部分修订 / 已取代（三态说明见下方「冻结后的修订标注」）

## 日期
YYYY-MM-DD

## 背景与问题
<要解决什么问题，现状的痛点。用产品/用户视角说清「谁、在什么场景、遇到什么」。>

## 目标 / 非目标
- 目标: <这次要达成的，可衡量>
- 非目标: <明确不做的，划清边界防蔓延>

## 设计决策
> 关键选择 + 取舍 + 为什么。每条决策让读者明白「为什么是这个方案，而不是别的」。

### D1: <决策标题>
- 选项: <A> / <B>
- 决策: <最终选择>
- 理由: <为什么；对体验/成本/风险的影响>
- 影响: <带来的后续约束或改动>

## 技术方案
<架构 / 数据流 / 关键接口 / 数据结构。复杂处配文字图或表。
 写到「读者能据此判断可行性与工作量」的颗粒度，不必写到代码级——代码级留给 sprint 的 PLAN。>

## 成功标准
- [ ] <具体的、可验证的标准>

## 范围
- 包含: <涉及的模块/功能点>
- 不包含: <明确排除的>

## 实现期重点清单
> 有意把边界/时序/并发/异常路径留给实现期 + 测试钉死的点，逐条列出。
> 这不是没想清楚，而是「纸面穷举边际递减、交给测试更可靠」的刻意收敛。sprint 验收时逐项核对覆盖。
- [ ] <边界/时序/并发/异常 点>

## 风险与未决
<已知风险、暂时悬置的问题、依赖的外部前提。无则删。>
```

## 冻结后的修订标注

定稿的 spec 是决策蓝图，记录「当初为什么这么定」，因此只追加不改写：被后续决策推翻时不重写正文，而是打标注指向新依据。正文重写会让读者失去判断历史决策的依据，也让引用过该章节的 sprint 文件失去落点。

### 状态字段三态

| 状态 | 含义 | 写法 |
|---|---|---|
| 定稿 | 全文仍然有效 | `定稿（冻结于 commit <sha>）` |
| 部分修订 | 部分章节被后续 spec 推翻并已标注，其余仍有效 | `部分修订（原定稿冻结于 commit <sha>；<被推翻章节名> 见 ai/specs/<新 spec>.md）` |
| 已取代 | 整份被新 spec 取代，读者应直接看新 spec | `已取代（以 ai/specs/<新 spec>.md 为准，YYYY-MM-DD）` |

### 章节标注格式

在被推翻章节的标题下第一行插入，正文一字不改：

```markdown
### D3: <原决策标题>

> ⚠ 本节已修订：以 ai/specs/2026-08-20-<新 topic>-design.md 为准（2026-08-20）
```

被推翻的是整段章节（如「技术方案」）时同样加在该章节标题下第一行。

同一章节被多次推翻时追加新标注行、保留旧行，按时间先后排列，读者能看到完整的推翻链。

### 触发时机

标注动作由**推翻它的新 spec** 在定稿流程中执行，不是等有人读到旧 spec 才发现过时。新 spec 定稿时逐项核对：本次的决策推翻了哪些旧 spec 的哪些章节 → 回去打章节标注 → 更新旧 spec 状态字段 → 与新 spec 同一次 commit 提交。

## 定稿前自检清单

写完通读一遍，发现问题就地修，不必反复重审：

1. **占位符扫描**：有没有 TBD / TODO / 「待补充」/ 「类似上面」这类没写完的地方？补全。
2. **内部一致**：各段有没有自相矛盾？技术方案和成功标准、范围对得上吗？
3. **范围聚焦**：是不是聚焦到「一轮 sprint 能实现完」的程度？如果横跨多个独立子系统，拆分再各自出 spec。
4. **歧义检查**：有没有能被两种方式理解的表述？挑一种写死、说明白。
5. **推翻核对**：本 spec 推翻了旧 spec 的结论吗？推翻的章节都打了标注、旧 spec 状态字段都更新了吗？
