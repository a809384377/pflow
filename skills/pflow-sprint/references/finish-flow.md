# 结束 Sprint 流程

Sprint 结束有两种状态：
- **completed**: 成功标准达成
- **closed**: 未完成就结束（中断/放弃/方向变更）

## 流程

```
1. 确认结束状态
   |- completed: 逐项核对 BRIEF.md 成功标准，全部通过则继续
   +- closed: 与用户确认关闭原因（中断 / 放弃 / 方向变更）

2. 未完成工作处理（closed 时）
   检查 PLAN.md 中 [ ] 或 [wip] 的 Step:
   |- 有未完成 -> 逐条询问用户是否写入 ROADMAP
   +- 无未完成 -> 继续

3. 追加 Sprint 总结到 LOGBOOK.md
   - 状态段改为 completed / closed
   - 末尾追加 Sprint 总结（模板见 references/templates.md）
   - 总结只写: 目标与结果对照 + 后续注意事项

4. 踩坑教训提炼
   如 LOGBOOK 踩坑记录段有内容:

   a) 逐条过门禁 -- 每条踩坑必须同时通过以下三关，任一不过则淘汰:
      G1 原则级: 能否脱离具体库名/函数名/参数独立表述？不能 -> 淘汰
      G2 可迁移: 换一个模块或项目还成立吗？不成立 -> 淘汰
      G3 模式级: 描述的是可复现的思维方式还是一次修复？后者 -> 淘汰
      校准: "prompts 库 ESC 需 monkey-patch exit()" = 具体方案，淘汰
             "第三方库覆盖默认键绑定时，patch 点要追踪上游变更" = 仍太具体，淘汰
             "进程标识靠唯一 ID 文件，不靠运行时命令名匹配" = 可迁移模式，通过

   b) 存活条目按 KNOWLEDGE.md 现有表格格式起草:
      规则 -> | R-N | 范围 | 规则 | 原因 | 来源 Sprint |
      模式 -> | P-N | 模式 | 适用场景 | 备注 |
      编号接续现有最大值

   c) 向用户展示起草结果，明确标注每条通过了哪三关
   d) 用户确认 -> 追加到 ai/KNOWLEDGE.md 对应表格
      用户否决 -> 仅保留在 LOGBOOK 中

   无踩坑记录或全部淘汰 -> 跳过

5. 回写结构真相
   读标注: grep -m1 '^结构真相体系:' ai/PROJECT.md
   |- 含「已启用」 -> 执行下方「回写协议」，红灯清零才能进入步骤 6
   |- 含「未启用」 -> 整步跳过，不向用户提任何一句
   +- 无命中（体系落地前的老项目）-> 一次性提示，不阻塞收尾:
      "本项目没有结构真相标注。想补建架构文档体系可以走 /pflow-init 的接管已有项目路径；
       确定不用的话我在 ai/PROJECT.md 写入「结构真相体系: 未启用」，以后不再问。"
      用户当场选就照做；不选也直接进入步骤 6，本次收尾不再追问

6. 归档 sprint 目录
   ai/sprints/active/<name>/
     -> ai/sprints/archive/YYYY-MM-DD_<status>_<name>/

7. 更新 ROADMAP
   |- completed: 标记对应条目 [x] + 追加归档路径；新问题追加
   +- closed: 询问用户是否调整对应条目标记

8. 提交变更
   git status 查看当前状态，与用户确认提交范围后 commit
   （步骤 5 回写的真相文件随这次 commit 与代码一并入库；启用结构真相体系的项目
    在 commit 前把校验件再跑一次，兜住步骤 7 刚写入的归档路径）

9. 生产环境同步（如适用）
   如 sprint 涉及 skill 文件变更，询问用户是否同步到各 agent 的 skill 目录
   （~/.claude/skills/、~/.pi/agent/skills/、~/.codex/skills/），同步后逐目录 diff 核对一致
```

## 回写协议（步骤 5 展开，仅标注为「已启用」时）

真相文件（`ai/tech-design/`）描述系统**当前**如何运作，是竣工图；本轮改完代码就是它唯一能被更新的时刻。回写的判断标准是「文档现在与代码一致吗」，不是「本期改了什么」——变更说明、旧行为对照属于 LOGBOOK，不进真相文件。

### 0. 取本期改动清单

```bash
START=$(git log --diff-filter=A --format=%H -- ai/sprints/active/<name>/BRIEF.md | tail -1)
git diff -M --name-only "$START"..HEAD
git status --short        # 尚未 commit 的改动一并纳入
```

`-M` 让改名显示为一条 rename，避免把文件搬移误判成「新增机制」。BRIEF 未入库时，用用户确认的起点 commit 或 `git log --since=<sprint 创建日期>` 代替。

**快速通过路径**：清单里没有源码文件（本期只动了 `ai/` 下的过程文件、文档或配置）→ 跳过第 1-4 步，只跑第 5 步的校验件，红灯清零即进入归档。纯过程 sprint 不做空转仪式。

### 1. 反查受影响的机制文档

把改动的源文件逐个到 `ai/tech-design/code-map.md` 的「机制/概念 → 源文件」表里反查，得到本期受影响的机制文档清单。反查不到的改动文件先记下来，进第 3 步。

### 2. 逐份复核回写

| 本期对该机制做了什么 | 回写动作 |
|---|---|
| 行为、边界、协作关系或失败路径变了 | 改正文对应段落，并刷新 frontmatter `last_reviewed` |
| 只改了实现（签名、内部结构），文档描述仍成立 | 只刷 `last_reviewed` |
| 机制被删除或并入其他机制 | 建议删除或合并该文档（清单级变更，须用户确认），同步清理门户路由表与 code-map 条目 |

### 3. 登记新增

- **新增机制**（改动落在既有机制文档都讲不到的地方）→ 列出建议新建的文档与职责，**经用户确认**后按 pflow-init 的 `references/truth-doc-templates.md` 建档，并登记进门户的「文件清单」与「问题式路由表」。机制清单定义真相体系的边界，属产品决策，不自行增删。
- **新增源文件** → 登记到 `code-map.md` 反查表对应机制行；测试、资源、构建产物不登记（校验件按豁免清单放行）。
- 新增或改名条目后，检查门户系统级图与 code-map 模块地图是否要加节点；节点显示名必须与 code-map 条目名完全一致。

### 4. PROJECT.md 能力主线

本期落地的是里程碑级能力（用户可感知的新能力、新入口、新交付形态）→ 在 `ai/PROJECT.md` 的能力主线补一行。内部重构、bug 修复、参数调整不写。

### 5. 跑校验件

```bash
bash ai/tech-design/check.sh      # 或项目已挂上它的测试命令
```

- **红灯**（L1 文档中的源码路径失活 / L3 指向 `ai/` 的文件指针失活）→ 必须清零，清零前不进归档。
- **黄灯**（L2 源文件未登记 / L4 图节点名与 code-map 不一致 / L5 `last_reviewed` 超期 / L6 文档超长）→ 逐条消化；确实要留置的，在 LOGBOOK 写明留了什么、为什么。L6 提示的膨胀用拆分或提炼处理，不靠继续追加绕过。
