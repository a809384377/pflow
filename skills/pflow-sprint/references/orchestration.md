# 编排执行：sprint 的交接与检查点节奏

> sprint 由主会话托管、派 subagent 执行时，按本文件组织交接、检查点和运行形态。何时派、派活单怎么写、审查、验收、修复与刹车这些通用做法见 dispatch skill（附派活单、审查单示例），派 subagent 前先加载它。

## 1. 交接分层

「主会话只读结论」要落地，靠把文件分成两层：

| 层 | 谁读写 | 内容 |
|----|--------|------|
| **交接区** | 主会话写，subagent 按需读 | `PLAN.md` 内联状态（进度真相源）+ `LOGBOOK.md` 执行进度段（跨 Step 接口契约、验收要点）+ 决策记录段 |
| **过程草稿** | subagent 私有，**主会话不读**（报告除外） | `ai/scratch/` 下的中间产物 + 子 agent 自己上下文里的过程 |

执行者把跨 Step 契约要点写进回报，主会话摘入 LOGBOOK 执行进度段，**只写指针 + 关键对接点**，如"Step 2 给 Step 3 的对接点是 X，函数签名/字段/端点细节见 `ai/scratch/stepN-notes.md`"。执行进度段每次会话启动和派活都要读，保持薄，细节留在 scratch。

在跑的 agent 也是进度真相的一部分：Step 标 `[wip]` 时，在该 Step 下记一行「执行: <agent 名称> · 报告: <scratch 路径>」。上下文被压缩或换新会话后，据此找回在跑的工作，不靠记忆。

## 2. 段与检查点

PLAN 按逻辑段组织。段内相关的连续 Step 交给同一个实现 agent 推进，不每步停审；段末 `[检查点]` 集中做一次审查与验收。主会话托管 sprint 时，段内的执行类工作默认派出，自己只编排、把关、推进。

检查点流程：

```
1. 以本段开工前的 commit 为对照基准，派一个独立 agent 兼做审查与验收；改动量大或高风险时拆成两个并行
   （派谁、审查单写法见 dispatch「审查与验收」）。报告原文落 ai/scratch/，不抄进 LOGBOOK
2. 逐条核实审查发现并分级：必修 / 可选 / 仅记录（过滤做法见 dispatch「审查与验收」）
3. 按 dispatch「审查与验收」的两层呈报给用户（全量层 + 决策层），用户拍板采纳哪些
4. LOGBOOK 决策记录段写最终处置结论 + scratch 报告指针；
   本段主会话代做的非关键决定一并列出（决定 / 理由 / 错了的代价）
5. 修必修项：打回原实现者还是换新 agent、何时刹车，按 dispatch「修复与刹车」；修后只审修复部分
6. 过段：按 progress-flow.md 检查点子流程汇总确认（可与第 3 步合并呈报），
   本段 Step 与检查点标 [done]，进下一段；会话要结束时整段覆盖 HANDOVER.md
```

未派 subagent 的简单 sprint 不走这套流程，检查点按 `progress-flow.md` 的汇总确认即可。

## 3. 运行形态

| 形态 | 适用 | 机制 |
|------|------|------|
| **交互式**（默认） | 高风险段（起停进程、改数据库结构或真实数据、不可逆操作）**强制** | 主会话在场连续派发、逐段把关；检查点、审查结论、重大决策才停下找用户 |
| **/loop 自主** | 低风险 / 机械段 | 主会话自动一段段往下跑，仅在检查点和阻塞时唤醒用户 |

形态在 create 时按段标注风险来定（见 PLAN.md 的「执行编排」段）。loop 自主跑偏的风险更高，前提是 spec / PLAN 足够硬；只要某段要起停进程、改数据库结构或真实数据、做不可逆操作，就回到交互式；只是读写数据的普通业务代码不算。危险与不可逆操作由主会话亲自做或经用户确认后做，见 dispatch「危险与不可逆操作」。
