# 编排执行：主会话派 subagent 干活

> 当 sprint 的工作量大到值得分工时，主会话不亲自下场写代码，而是当总指挥：派 subagent 执行、派独立 agent 审查、自己只读结论并把控节奏。这样主会话的上下文留给编排和判断，不被实现细节填满。

## 1. 何时编排 vs 直接做

编排有成本——派一个 subagent 要准备自包含的上下文，子 agent 跑一趟也烧 token。所以它只在收益大于成本时才值得。

**直接做（主会话亲自改，不派 subagent）**：机械确定的小修——缺文件、改文案、改常量、清缓存、单文件的明确改动。这类活准备派活上下文的功夫比自己改还久。

**值得编排**：多步实现、跨多个文件、需要独立对抗审查、或起进程/跑测试这类会大量占用上下文的验证。

判别：这个 Step 如果主会话自己做，会不会把上下文塞满实现细节、挤掉编排所需的全局视野？会 → 派出去。不会 → 直接做。

> 不要为了"用上编排"而硬拆简单工作。也不要把契约还没定的强耦合改动拆给互不知情的子 agent——契约不稳就同段一个 subagent 做完，拆了反而被交接成本和返工吃掉收益。

## 2. 三角分工

| 角色 | 默认归属 | 职责与纪律 |
|------|---------|-----------|
| **实现** | claude subagent（完整权限） | 在自己上下文里闭环：写代码 + 自测 + 验证。大产出落 scratch/artifacts，**只回一句结论**给主会话。 |
| **评审** | codex（只读沙箱）；无则独立 subagent | **仅在段末检查点**触发。对抗式攻击实现，不是复核。**只看产出 + spec，不看实现者的思路**。结论分两层呈用户：全量忠实 + 决策摘要（见 §6）。 |
| **验收** | 主会话亲做 | 逐 Step 轻量验收（读结论）+ 段末复验（跑全量 / 读关键代码 / 残留扫描）。这是主会话把控节奏的核心动作，不外包。 |
| **修复** | 原实现者 subagent 续上下文 | 审查打回的问题，交回当初写它的 agent——它记得为什么这么写。多处修复可分批并行，但避开同一文件并发改。 |

**为什么评审要独立、且不给它实现者的思路**：同一个 agent 自审，受锚定偏见，得到的是「第一版的换皮」而非第二意见。换一个 agent、最好换一个模型（codex），只喂它产出和 spec，它才会真正去挑毛病。

**为什么验收留主会话**：主会话靠验收结论决定「这段过没过、下一步派什么」，这是编排判断力的来源。把验收也外包，主会话就成了只会转发的传声筒，失去节奏感。

**危险操作的归属**：起/杀进程、占端口、改生产数据、任何不可逆操作，留给完整权限的实现 agent 或主会话亲跑。**沙箱受限的评审 agent（codex）绝不碰这类操作**——它会挂死或权限不足。结合本项目 `ai/KNOWLEDGE.md` 里的相关规则执行。

## 3. 派活模板（给实现 agent）

主会话与子 agent 之间唯一的通道，就是派活时的这段 prompt。子 agent **拿不到主会话的历史和对话**，所以 prompt 必须自包含——四要素缺一不可：

```markdown
【目标】
<这个 Step 要做什么。把 spec 相关章节的原文贴进来，不要让子 agent 自己去翻文件——
 你已经知道它该看什么，替它准备好最省事。>

【上下文】
<前序 Step 留下的接口契约（从 LOGBOOK 执行进度段摘）、本项目 KNOWLEDGE 相关规则、
 涉及的现有代码位置。给足它理解「这个改动嵌在哪」的信息。>

【产出格式】
完成后回报：状态 + 接口契约要点 + 验证结果。状态取：
- DONE：做完且自测通过
- DONE_WITH_CONCERNS：做完但有疑虑（说明疑虑）
- NEEDS_CONTEXT：缺信息做不下去（说明缺什么）
- BLOCKED：遇到无法解决的障碍（说明卡在哪）
大块产出（日志/中间文件）落 ai/scratch/，**只把结论回给我**，不要把全文灌回来。

【边界】
<不要碰什么：范围外的文件、危险操作清单。明确划界防越权和误伤。>
```

**收到回报后怎么办**：
- DONE → 进入验收/或攒到段末检查点。
- DONE_WITH_CONCERNS → 先看疑虑：涉及正确性/范围的先处理，纯观察（如"这文件有点大了"）记下继续。
- NEEDS_CONTEXT → 补上缺的信息，重新派同一个 agent。
- BLOCKED → 别让同一模型原样重试。判断是缺上下文（补了再派）、需要更强推理（换更强模型）、任务太大（拆小）、还是计划本身错了（找用户）。

## 4. 评审模板（给审查 agent）

评审的价值在于**独立对抗**——构造实现者没想到的用例去攻击它，而不是确认已有测试通过。

```markdown
【任务】
对抗式审查 Step <X–Y> 的实现。你的目标是找出实现者没覆盖到的盲区——
独立构造对抗用例攻击它：编码/转义、空输入、EOF、嵌套、并发/竞态、畸形输入、超长/边界值。

【给你的材料】
- 产出：<git diff 或文件清单/内容>
- 依据：<spec 相关章节原文> + 成功标准
（注意：这里不提供实现者的思路和过程——请基于产出本身独立判断。）

【产出格式】
分级列出问题：Blocker（必须修）/ Major / Minor。每条给：现象 + 复现路径 + 定位（文件:行）。
没问题就明说"未发现问题"，不要凑数。
```

**模型选择**：评审优先用 codex（不同模型 = 更独立的第二意见，且只读对抗不碰危险操作很安全）。环境没有 codex 时，派一个独立的 claude subagent，同样只喂它产出和 spec。

## 5. 交接分层

「主会话只读结论」要落地，靠把文件分成两层：

| 层 | 谁读写 | 内容 |
|----|--------|------|
| **交接区** | 主会话 + subagent 都读写 | `PLAN.md` 内联状态（进度真相源）+ `LOGBOOK.md` 执行进度段（跨 Step 接口契约、验收要点）+ 决策记录段 |
| **过程草稿** | subagent 私有，**主会话不读** | `ai/scratch/` 下的中间产物 + 子 agent 自己上下文里的过程 |

实现 agent 把跨 Step 要传递的契约写进 LOGBOOK 执行进度段，但**只写指针 + 关键对接点**——如"Step 2 给 Step 3 的对接点是 X，函数签名/字段/端点细节见 `ai/scratch/stepN-notes.md`"，不把实现细节全文抄进来。原因：执行进度段是高频读区（会话启动要读、派下一个 subagent 要把它摘进 prompt），越厚每次接力越贵；细节留 scratch，需要时再点开。大块过程产物一律留在 scratch 或子 agent 自己上下文里。主会话顺着这个薄交接区就能接上下一步，不必去读任何过程细节——这正是保护主会话上下文的关键。

## 6. 段末检查点

PLAN 按逻辑段组织，段内多个 Step 由实现 agent 连续推进、不每步停审；段末 `[检查点]` 才做一次集中验收+评审：

```
1. 派评审 agent 对本段实现做对抗审查（见 §4）；评审报告原文（含 verbatim）落 `ai/scratch/`，**不抄进 LOGBOOK**——LOGBOOK 只留处置结论 + scratch 指针
2. 评审结论分两层呈用户：先全量忠实翻译（都报、不软化、保留来源），再附一段「决策摘要」筛出真正要用户拍板的、总结成"要定什么"——详见下方说明
3. 主会话双轨核实：复核评审每一条，可下调误判等级、纠正过判（评审也会看错）
4. 用户拍板采纳哪些
5. 打回原实现者续修（见 §2 修复行），多处可分批并行避同文件冲突
6. 主会话复验：跑全量回归（不只跑相关测试）+ 读关键代码确认不变式 + 残留扫描
7. 过段，进下一段
```

**呈报评审结论：分两层，让用户聚焦决策**。评审报告天然是技术语言，还常把"影响产品的硬决策"和"纯内部技术确认项"混在一起，逼用户自己大海捞针——决策摩擦很高。所以分两层呈报，目标是让用户大概率只看第二层就能拍板：
- **第一层 · 全量忠实**：所有发现都翻译成产品语言列出，保留来源和证据、不软化严重程度、不私自删减。用户想深挖时这层都在，信息不藏。
- **第二层 · 决策摘要**：从全量里筛出真正需要用户拍板的，每条总结成"用户会看到什么现象 / 影响什么 / 要在 A 还是 B 之间定什么"。判别一条要不要进这层，只看它是否影响架构、扩展性、产品决策、设计或用户体验——影响就进（哪怕技术性很强，比如一个会让用户踩到崩溃的 bug）；纯内部、产品和用户都感知不到的技术确认项（命名、注解、接口契约确认等）留在第一层即可。

这层是"帮用户聚焦该看什么"，不是"替用户拍板采纳什么"——筛的是呈现优先级，决策权始终在用户，全量层也没有信息被藏起来。

**涉及 UI / 交互 / 异步状态机的改动，叠加双轨验证**：真环境 e2e（黑盒，抓时序/渲染/环境盲区）+ 代码审查（白盒，抓并发/边界/推演盲区）并行跑，两路独立报告再合并——「查得到 ≠ 用户看得见/没越权」，谁也替代不了谁。

## 7. 运行形态

| 形态 | 适用 | 机制 |
|------|------|------|
| **交互式**（默认） | 高风险段（进程/数据/不可逆）**强制** | 主会话在场连续派发、逐步验收；检查点、评审结论、重大决策才停下找用户 |
| **/loop 自主** | 低风险 / 机械段 | 主会话自动一段段往下跑，仅在检查点和阻塞时唤醒用户 |

形态在 create 时按段标注风险来定（见 PLAN.md 的「执行编排」段）。loop 自主跑偏的风险更高，前提是 spec / PLAN 足够硬；只要某段触及进程/数据/不可逆，就回到交互式。
